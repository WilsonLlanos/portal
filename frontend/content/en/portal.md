# Portfolio Portal with AI Chat — how it works

## Portal overview
The Portal is Wilson Llanos's portfolio website: a bilingual site (Portuguese and English) with an AI assistant that answers questions about his career. The assistant uses RAG (Retrieval-Augmented Generation) over the portfolio's own content: résumé, experience, projects, certifications and this technical description of the site. The code is open source (github.com/WilsonLlanos/portal) and was built with Spec-Driven Development.

## Portal architecture and stack
The frontend uses Next.js 16 (App Router), TypeScript, Tailwind CSS 4, next-intl for the /pt-BR and /en routes, and next-themes for light and dark themes. Pages are pre-rendered at build time (SSG). The backend is Python 3.12 with FastAPI, managed with uv. Frontend and backend are deployed as two separate projects on Vercel. The chat answers by streaming (Server-Sent Events). Content lives in versioned files under frontend/content/, and the same source feeds both the pages and the chat's knowledge base, so what the site shows and what the chat knows never diverge.

## Chat pipeline, step by step
Each question goes through these steps, in this order: (1) message length validation (up to 500 characters); (2) daily cost cap check; (3) per-visitor rate limit; (4) prompt-injection guardrail (InputGuard); (5) retrieval of relevant excerpts from the knowledge base (RAG); (6) prompt assembly with the retrieved context and the short conversation history; (7) answer generation by the LLM, streamed; (8) logging of the interaction for observability. The server keeps no conversation state: the client sends the last 4 messages along with the question.

## RAG: ingestion and knowledge base
The knowledge base is built by the backend/scripts/ingest.py script. It reads the content in frontend/content/ in both languages, splits the text into chunks of about 180 words (or by section, for this technical description) and creates an embedding for each chunk with Google's gemini-embedding-001 model. The output is saved as files in backend/data/kb/: chunks.json (text and metadata such as language and source), vectors.npz (the embedding matrix) and manifest.json (model, dimension, date and a content hash). A GitHub Actions check compares that hash with the current content and blocks the merge if the knowledge base is out of date.

## RAG: vector search without a vector database
The Portal does not use a vector database. Since the knowledge base is small, search runs in memory with NumPy using cosine similarity, behind a VectorStore interface (FileVectorStore) that allows swapping in a vector database such as Qdrant later. For each question, the backend embeds the message with the same model, filters chunks by the session language, computes cosine similarity against all of them at once (a matrix multiplication) and sends the 5 most similar to the LLM (top_k = 5). On startup, the backend checks that the manifest's embedding model matches the configured one, so incompatible vectors are never compared. Alternatives considered and rejected: Qdrant Cloud (suspends on inactivity), Chroma (disk persistence doesn't work in serverless) and pgvector (overkill for this volume).

## Answer generation (LLM)
Answers are generated by Google Gemini, through the google-genai SDK, behind an LLMClient interface that allows switching providers by configuration. Temperature is 0.4 and output is capped at 512 tokens per answer. The system prompt requires answering only from the retrieved context, admitting when the answer is unknown, and replying in the language the visitor wrote in. The Portal uses Gemini's paid tier with a limited budget, because on the free tier Google may use submitted content to improve its products.

## Security: prompt-injection guardrail
Before any search, the question goes through Llama Prompt Guard 2 (86M), Meta's prompt-injection classifier, called through the Groq API. It returns an attack probability, and the backend blocks the question at 0.5 or above, replying with a polite refusal. Local regex heuristics in Portuguese and English add another layer. The policy is fail-open with degradation: if Groq is slow (2-second timeout) or down, a circuit breaker stops calling it for 60 seconds after 3 consecutive failures, and the chat keeps working with local defenses only.

## Cost limits and rate limiting
To control cost and abuse, the Portal limits each visitor to 20 questions per hour and has an estimated daily cost cap of 50 US cents; when the cap is reached, the chat pauses until the next day. Counters live in Upstash Redis, because serverless functions don't share memory. Visitors are identified by a hash of IP and user agent with a daily salt, without storing the IP. If Redis fails, a stricter in-memory limiter takes over (10 questions per hour): for cost, the policy is fail-safe.

## Observability, testing and CI/CD
Every chat interaction is traced in Langfuse Cloud (language, outcome — answered, refused, no answer or error —, guardrail result, IDs of the retrieved chunks, tokens and estimated cost, with no personal visitor data), alongside structured JSON logs and a GET /health endpoint. Tests use pytest and ruff on the backend, and Vitest, ESLint, Playwright (with accessibility checks) and Lighthouse CI on the frontend, plus evaluation sets with real questions and attacks. GitHub Actions runs backend CI, frontend CI, the knowledge-base freshness check and a scheduled production health check every 30 minutes. The main branch is protected and only accepts pull requests with green checks. Deployment uses Vercel's native Git integration.

## Spec-Driven Development
The Portal was built with Spec-Driven Development (Spec Kit): first a constitution with the project's principles, then the specification (spec.md), research with the technical decisions (research.md), the plan (plan.md), the data model and the task list (tasks.md), and only then the implementation. These artifacts live in specs/001-portfolio-portal/ in the repository.
